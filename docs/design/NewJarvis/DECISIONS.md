## D1 · 记忆迁移映射

**日期**：2026-10-24 ｜ **状态**：已定（用户确认）

`memories.memory_type` 迁移到新 `layer`：

| 旧 `memory_type` | 新 `layer` | 新 `status` |
| --- | --- | --- |
| `episodic` | `short` | `confirmed` |
| `fact` | `long` | `confirmed` |
| `preference` | `long` | `confirmed` |
| 其它 / 空 | `short` | `confirmed` |

**理由**：`episodic` 语义是"发生过的事件摘要"，天然属于短期；`fact`/`preference` 是稳定事实，进长期。
**代价**：历史上用 `fact` 记录的事件型内容会变成长期记忆，可能偏多。**缓解**：迁移脚本输出统计，
跑完打印各层条数供人工抽查；不自动忘记任何记录。

## D2 · 导航形态与对话入口

**日期**：2026-10-24 ｜ **状态**：已定（用户授权代为决定）

### 结论

1. **导航保持 5 个平级顶部 tab，不做浮动卡片式导航。**
2. **加一个全局"待许可悬浮条"**，这是唯一允许的悬浮元素。
3. **对话并入活动流**：顶部一条"直接回复"输入栏，历史对话以可折叠卡片出现在活动流里。
4. console 现有的独立 `AI 对话` 视图删除。

### 理由

- 控制面的第一需求是**稳定的肌肉记忆**：第 3 个 tab 永远是记忆库，不该因为窗口位置变化而找不到。
  浮动卡片会引入 z-order、拖拽、遮挡、多显示器还原等一系列成本，收益只是"看起来现代"。
- 5 项在 960px 下不拥挤；窄于一屏时折叠成下拉选择，不需要改变信息架构。
- **但你的直觉有一个点是对的**：高风险待许可必须能从任何 tab 一步到达，而不是先切回活动流。
  这个需求用"导航解决"是错的，用"悬浮提醒"解决才对——所以只做这一条悬浮条。
- 对话不是主界面。草图里没有聊天窗口是对的：Jarvis 的价值在"替你判断"，不在"陪你聊"。
  把对话降级为活动流里的一个动作（对某条活动直接回复），语义更清楚：**回复永远是针对某件事的**。

### 待许可悬浮条规格

```
位置     右下角固定，距边 24
出现     仅当存在 attention=high_risk_waiting 且未过期
收起     可点"稍后"收起 10 分钟（不消失，缩为一个 8px 红点）
点击     跳到 01 活动流，滚动并高亮该卡，自动展开依据
高度     48–56，宽随内容；颜色用语义红，不用整块铺色，只描边 + 红点
禁止     不得用于低风险提示（那会变成新的噪声源）
```

### 代价

- 活动流会同时承载"流"和"对话输入"，同屏信息密度上升。**缓解**：输入栏默认折叠为一行，
  点击展开；只在用户主动回复时展开。
- 删除 chat 视图后，`sessionStorage` 里的历史聊天记录需要一次性迁到服务端 `conversations`，否则用户会觉得"记录丢了"。

## D3 · trusted_mode 退役

**日期**：2026-10-24 ｜ **状态**：已定（用户确认：由主 Agent 持有受信授权）

### 结论

删除全局布尔 `trusted_mode`，改为**一条显式的、可查看可撤销的授权记录**：

```jsonc
{
  "subject": "agent:god",
  "level": "once",                 // 绝不是 per_action 的高风险能力
  "capabilities": ["memory.read", "draft.create", "reminder.write", "project.read"],
  "scope": {"kind": "project", "value": "*"},   // 仅限用户自己的项目
  "expires_at": "…",               // 必须有过期时间
  "revocable": true,
  "excludes": ["message.send", "payment.execute", "device.configure",
               "device.self_iterate", "device.remote_exec"]
}
```

**规则**

1. 主 Agent 通过这条 grant 工作，权限**只能收窄**，不能自我修改、不能续期。
2. `excludes` 是硬编码常量，不参与配置——高风险能力永远不可能被这条 grant 覆盖。
3. 授权在"权限门控"页可查看、可撤销、可改范围与有效期，每次变更写审计。
4. 兼容期：环境变量 `TRUSTED_MODE=1` 仍在时，启动时生成等价的 grant 并记
   `granted_by=trusted_mode_legacy`；M3 结束后该兼容路径移除。

**理由**：把"隐藏的布尔"变成"看得见的一条授权"，正好是这个版本的核心命题。
**代价**：多一张表、多一套 UI。但权限门控页本来就要做，边际成本低。

## D4 · 全量销毁进 v1.0

**日期**：2026-10-24 ｜ **状态**：已定（用户确认加入）

### 结论

进范围，但定为**全系统最高风险操作**，实施约束：

1. 前置：`kill_switch` 先置位，停止一切调度。
2. 强制导出校验：必须点击"导出需要保留的数据"并成功，才解锁下一步。
3. 二次确认识别：必须精确输入 `销毁全部`（不做模糊匹配、不允许粘贴带空格）。
4. 备份窗口：主库立即清空，备份标记 7 天后到期物理删除。
5. 回执保留：留不含任何原文的执行回执（动作、时间、条数、grant ID）。
6. 文案必须写明：**已送达的外部消息不会因此被删除**。

### 理由

用户明确要求加入；且草图为它设计了完整的危险区交互。
### 风险

不可恢复。**缓解**：以上 6 条缺一不可；接口层面再做一次"必须带 confirm_token"的校验，
避免前端 bug 直接调用；测试环境不得跑真实销毁。

1. 每个任务只改 brief 里列出的文件；越界修改必须回退。

   - 交付说明只报"新增 N 条，通过 N 条"，不贴完整 diff、不复述代码；
   - 全量测试、回归判定、提交，全部由统筹方执行。
6. 一次任务只交一件事；宁可拆成两次调用，也不要一次吃下整个里程碑
   （M0.1 单次消耗 39 万 token，其中大量是重复打印 diff）。

## D6 · 放弃旧后端兼容，v2 从零重建

**日期**：2026-10-24 ｜ **状态**：已定（用户确认）

### 结论

1. **不做数据迁移**。旧库 `data/jarvis.db` 只作为只读档案保留，新库从零建。
2. 内部结构（schema、服务分层、Agent 运行时）全部重写，见
   [AGENT_FRAMEWORK.md](AGENT_FRAMEWORK.md)。
3. **但保留边缘 HTTP 契约**：活动流、许可、记忆、设备指标这些中控与手表在用的接口
   形状不变。换的是内部实现，不是用户已经验收过的界面。
4. v1.0 已完成且被证明正确的四个模块**直接沿用**：权限矩阵与 grant、
   记忆分层与候选、活动四层依据、设备会话与 kill switch。

### 理由

生产数据说明旧后端的问题不在接口层，而在三处内部结构：
门控会误丢真信息（作业被 ignore）、任务会卡在没有终态的中间状态、
原始遥测被逐条写进长期记忆（11 条记忆里 7 条是坐标流水）。
这些都要换骨架才能修，不是加接口能解决的。

### 代价

- 旧库里的 11 条记忆、12 个任务不带过来。其中"敏感话题规则"与"产品定位"两条是
  有价值的长期设定，**实施时需要用户重新确认后手动写入新库**（不自动搬运，
  因为无法判断旧数据是否仍然准确）。
- 中控与手表要按新 Run/Thread 字段做增量调整，但页面结构不变。
