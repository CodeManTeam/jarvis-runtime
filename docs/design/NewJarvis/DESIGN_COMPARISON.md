# NewJarvis 草图解读与现状差距分析

> **这是背景材料，不是实现基线。** v1.0 的设计与实现基线见 [README.md](README.md) 里的文档组。
>
> 输入材料：`docs/design/NewJarvis/PNG_Output/` 共 14 张草图

## 0. 一句话结论

草图不是"再画一套界面"，而是把产品从**"会聊天/会记日志的助手"**重新定义为
**"一个可授权、可核查、可回滚的个人自动化中控台"**——手表是它的注意力终端，中控是它的
驾驶舱。当前项目已经具备这条主链路的大部分**数据骨架**（事件、活动、审批、审计、设备命令、
预算），但**缺少草图里三个最核心的概念**：许可的作用域与有效期、AI 判断的置信度与四层依据、
以及降级/离线的显式状态。因此差距主要不在像素，而在**领域模型**。

## 1. 我读到的思考：六条设计主张

### 主张一：注意力是稀缺资源，产品只交付"值得你注意"的部分

- 手表首页标题直接是「值得你注意」，卡片分成四类且语义互斥：
  **高风险·等你** / **自动·已处理**（可撤销）/ **建议·确认一次** / **已忽略·AI 已知情**（可查看留痕）。
- 中控首页抬头是「把注意力留给真正重要的事」，四格指标是
  **有意义的事件 04 / 自动完成 12 / 等待你许可 01 / 最近同步 09:41**，
  并明确区分「有意义·4」与「全量记录·38」两个视图。
- 被忽略的东西**不是消失，而是降级为可追溯记录**，并且注明"AI 已知情"。

> 这解释了为什么草图里几乎没有"聊天窗口"：对话不是主界面，注意力流才是。

### 主张二：结论先行，证据分层，但不假装展示思维链

中控和手表用了同一套四层结构（手表第 3 屏「为什么这样做」、中控活动卡展开）：

| 层 | 内容 | 草图中的例子 |
| --- | --- | --- |
| 01 结论 | 发生了什么、可否撤销 | 14:30 复核提醒已添加，可撤销 |
| 02 判断与依据 | 截止时间、预留时长、**置信度 94%**、风险等级 | 15:00 截止，预留 30 分钟复核 |
| 03 引用 | 记忆 M-021 / M-034、事件 E-108、工具 T-044（可点击溯源） | 每条都有 ID 和"可查看原文" |
| 04 原始输入与门控 | 语音 V-012（可播放原录音）、ASR 原文、通知原文、门控记录 G-044 | 明确"点按查看"并留审计 |

并标注「记忆 2 · 工具 1 / 非内部思维过程」——既给证据，又给解释的上限，避免过度承诺。

### 主张三：授权不是"信任 Agent"，而是"能力 + 范围 + 有效期"的三元组

「权限门控」页是整套草图里信息密度最高的一页，它做了三件现在项目完全没做的事：

1. **四档门控**：自动 / 确认一次 / 每次确认 / 禁止，并且作用在**能力粒度**上
   （本地提醒、整理短期记忆、今天调整复核时间、写入长期习惯、读取未授权文件各占一行）。
2. **受信 Agent 的边界卡片**：明确列出"能力清单不含 message.send、不含支付、不含远程命令"，
   **范围**（仅"北岸提案"项目 + 已选联系人）、**有效期**（09:00–18:00，到期即失效，
   **不能由 Agent 自行续期**），以及"高风险例外：没有例外"。
3. **门控优先级**：`禁止 > 每次确认 > 限定许可 > 自动`，
   并写明"网络恢复、模型切换与重试均不能复用已消费的高风险许可"。

手表上的对应表达是两句极短的文案：
「确认发送一次」「许可仅用于本条消息 · 不授予长期权限」。

### 主张四：把"不可逆"讲清楚，而不是用"撤销"骗人

- 外发卡：「送达后无法保证撤回；只能追加更正，并记录补偿操作。」
- 编排页底部：「系统只承诺取消待发、保留送达回执及记录后续更正，**不伪造'全部撤销'**。」
- 中控有独立的「修改、删除与补偿轨迹」表，动作与"结果与边界"分列。
- 每条高危动作都区分**执行前可取消**与**执行后只能补偿**两种世界。

### 主张五：失败、降级和离线必须是一等公民 UI，而不是空白或"处理中"

- 手表「服务降级」：`ASR 备用路由也超时 → 文本输入` / `模型主路由超时 → 轻量模型接替` /
  `TTS 不可用 → 仅显示文字` / `附件工具失败 → 重试 1/2 已恢复`，
  并承诺"不会把失败标记为完成"。
- 手表「离线缓存」：`已缓存，没有离线执行`、`待补传通知 3 条`、
  "恢复后按事件 ID 去重补传。外发任务仍待许可，不会重放发送。"
- 中控「模型路由与降级」：J-Pro → J-Lite，写明切换原因、**能力限制**（"不扩大访问范围、
  不擅自外发、不自动改长期规则"）和恢复策略，并强调"降级不降低权限边界"。
- 每条失败都保留**原错误**（"重试 1/2 成功 · 原错误保留"），不做静默覆盖。

### 主张六：设备是省电、低配、常离线的真实硬件

- 低电量极暗模式：12% 时"持续感知已关闭"，但**明确保留**「长按语音」「文本输入」，
  并写死一条规则：「高风险许可不因省电而跳过」。
- 手表「安静待机」默认**不播报**，只在异常时亮屏；语音"仅按住时"生效。
- 设备页列出 1380mAh、小 RAM/小存储、**滚动缓存 16 条**、"仅触屏·无按键/旋钮"的交互约束，
  并把"≤15% 关闭持续感知"写成可核对的省电策略。

## 2. 草图定义的信息架构

```text
中控（单人驾驶舱，顶部 5 个平级 tab，无侧栏）
├─ 01 活动流        ATTN & AUDIT    有意义 / 全量记录、四层依据、补偿轨迹
├─ 02 Agent 编排    EXECUTION CTRL  执行计划 6 步、工具回执、模型路由与降级
├─ 03 记忆库        PERSONAL MEMORY 长期/短期/用户项目/AI 自建、时间线、忘记与销毁
├─ 04 权限门控      PERM BOUNDARIES 四档矩阵、受信 Agent 边界、远程配置内嵌二次确认
└─ 05 设备与模型    DEVICE & MODEL  在线率/延迟/错误率/Token/电流、多路由、APK 与自迭代、RCE

手表（9 个状态屏，全部单屏、无导航栏）
├─ 安静待机      时间 + 一句状态 + 抬腕详情
├─ 注意力流      四类卡片流 + 上滑更多 / 下拉刷新
├─ 四层依据      "为什么这样做"
├─ 高风险许可    草稿 + 不可逆警告 + 确认一次
├─ 语音输入      长按、流式转录、四段流水线、首响应≤5s
├─ 习惯建议      仅今天应用 / 忽略并留痕（不自动固化为长期习惯）
├─ 离线缓存      已缓存、不执行、按事件 ID 去重补传
├─ 服务降级      失败事实 + 保留文本通道 + 不伪装完成
└─ 低电量极暗    关感知、留长按语音与文本、不减免高风险许可
```

## 3. 逐屏对照：草图 → 现状 → 差距

### 3.1 手表（`watch-client`）

现状结构（`activity_main.xml`）：**单页滚动** = 状态头 → 远端服务器配置 → AI 介入开关 →
实时感知 → AI 活动主卡 → 时间线两条 → 查看日志。另有 `activity_settings.xml`、
`activity_log.xml`、活动详情对话框、`ThemeMode`（浅/深/跟随系统）。

| 草图屏 | 现状能力 | 差距 |
| --- | --- | --- |
| 安静待机 | 有状态头（`header_status_*`）、有感知文本，但**无时间/电量/日期行**，且首页首屏被"服务器配置/AI 介入"两块占位 | **中**：缺状态栏（时间·待办数·电量）、缺"抬腕详情"折叠、首页信息优先级要重排 |
| 注意力流 | 只有 1 张主卡 + 2 行纯文本时间线；卡片无风险等级、无"为什么"入口 | **大**：需要"卡片流 + 四类语义 + 每卡动作组"，且要服务端给出风险/建议/忽略分类 |
| 四层依据 | 详情对话框只有 `状态/来源/判断/结果/工具与流程/可用操作/活动 ID` | **大**：缺置信度、缺记忆/事件/工具的可点引用、缺原始输入与门控记录 |
| 高风险许可 | 卡片按钮"接受/暂不"，确认走 `pending_actions` | **中**：有机制无表达——缺草稿全文、收件人、附件、不可逆声明、"许可仅本条" |
| 语音输入 | 首页内 `toggleRecording()`，无独立输入页 | **中**：缺长按交互、流式转录展示、四段流水线、改用文本的等价入口 |
| 习惯建议 | 无 | **缺失**：无"候选/未固化"记忆类型，也无"仅今天应用"的作用域概念 |
| 离线缓存 | `RuntimeService` + 重连；无"待补传 N 条"任何 UI | **大**：缺离线态页面与补传计数（服务端已按事件 ID 去重，可直接暴露） |
| 服务降级 | 有 `perception_state_error`、TTS 失败 toast | **大**：缺"哪一环失败 + 已自动降级到什么"的结构化展示 |
| 低电量极暗 | 只上报 `battery_level` 给服务端（`MainActivity.getBatteryLevel()`） | **缺失**：无电量驱动 UI 策略、无极暗主题、无"关感知留文本"规则 |

> 注意：`docs/DESIGN_SYSTEM.md` 当前写明"先以浅色示意图为唯一验收基线"，背景 `#F7F5F0`。
> 草图是深色。这是**方向性冲突**，必须先拍板（见 §6）。

### 3.2 中控（`console`）

现状结构（`index.html` 侧栏 7 项）：实时感知 / AI 对话 / 任务队列 / 记忆与项目 / 忽略规则 /
设备 / 运行审计。浅色暖纸风格（`style.css` 变量 `--bg: #f7f5f0`）。

| 草图 tab | 现状最接近的视图 | 差距 |
| --- | --- | --- |
| 01 活动流 | 实时感知 + 运行审计（两处割裂） | **大**：没有统一"有意义/全量"流、没有四层依据、没有补偿轨迹表 |
| 02 Agent 编排 | 任务队列（只有标题/状态/时间/来源） | **很大**：无执行计划步骤、无工具回执表、无路由与降级面板、无暂停/接管/打断 |
| 03 记忆库 | 记忆与项目（两个平铺列表） | **大**：无时间线、无短期/长期/项目/AI 自建分层、无编辑修订、无忘记/销毁、无导出 |
| 04 权限门控 | 忽略规则（只有文本匹配过滤） | **缺失**：整个视图相当于不存在 |
| 05 设备与模型 | 设备（名称/平台/在线/最后在线） | **很大**：无指标（在线率/延迟/错误率/Token/电流）、无路由表、无远程配置/APK/自迭代/RCE |

顶部导航：草图是**平级 tab**，现状是**左侧竖栏**；草图的"编号 + 英文小标"章节感也没有。

## 4. 后端能力对照（决定 UI 能不能真做出来）

| 草图依赖的能力 | 现状 | 判断 |
| --- | --- | --- |
| 事件 ID、幂等、审计、游标分页 | `app/activity.py`：`available_actions`、`revision`、`etag`、`idempotency_key`、`next_cursor` | ✅ 已具备，甚至强于草图需要 |
| 待确认动作（含 payload、过期） | `pending_actions`（`expires_at`）+ `service.confirm_pending_action` | ✅ 骨架在，但**无"许可只覆盖本条"的显式作用域字段** |
| 设备命令生命周期 | `device_commands`：`pending→delivered→acknowledged/failed/expired` | ✅ 已具备 |
| 预算与限额 | `usage_daily`（ASR 秒 / 输入输出 token / 预留）+ `UsageLimitExceeded` | ✅ 已具备；**无延迟 P50/P95、无错误率** |
| 设备遥测 | `devices` 有 `battery_level/network_type/app_version/storage_free_mb/charging` | ✅ 字段够草图"设备与连接"卡用 |
| 自主等级 | `AutonomyLevel` 0–4 + `PolicyEngine`（含 `trusted_mode` 全局开关） | ⚠️ **是 5 档全局等级，不是"能力×范围×有效期"矩阵** |
| 置信度 | `events.confidence` 只是**输入置信度**；`PolicyDecision` 无 confidence | ❌ 草图的 94%/96%/81% 无字段来源 |
| 四层依据 | `activity.detail` 有 `reason/reply/waiting_for/task/memory_ids/history` | ⚠️ 有骨架，缺结构化 `judgment/evidence/raw refs`，`memory_ids` 只有 ID 没有可点原文 |
| 记忆生命周期 | `memories`：`content/type/project/source_event/importance/created_at` | ❌ 无 置信度/有效期/版本/冲突/候选态/TTL 清理/修订历史 |
| 模型路由与降级 | 无路由层；`llm.py` 单模型 + `UsageLimitExceeded` | ❌ 草图的 J-Pro→J-Lite 无实现基础 |
| 远程配置 / APK 升级 / 自迭代沙箱 / RCE 白名单 | 均无 | ❌ 全部是从 0 到 1 |
| 离线补传去重 | 服务端已有 `dedupe_key` + 事件去重 | ✅ 可支撑"按事件 ID 去重补传"，只差端侧计数与 UI |

## 5. 差距分三类（决定工作性质）

**A. 纯表达层（照图重画即可，1–2 周量级）**
手表状态栏/卡片流/极暗主题、中控 tab 化与章节化、表格化矩阵外壳、文案语气统一。

**B. 契约层（改 API 与数据表，牵动测试）**
- `Activity` 增加 `confidence`、`evidence[]`（memory/event/tool/raw 四类引用）、
  `grant`（scope、expires_at、single_use）、`degradation`（哪一环降级到哪）。
- `memories` 增加 `layer`(long/short/project/ai_candidate)、`status`(candidate/confirmed)、
  `confidence`、`valid_from/to`、`superseded_by`、`revision`、`raw_ref`。
- `usage_daily` 之外增加延迟直方图/错误计数（P50/P95、错误率）。
- 新增 `permission_grants` 表：capability × scope × level × expires_at × single_use × consumed_at。

**C. 概念层（现有架构没有对应物，必须新设计）**
1. **能力级权限矩阵**（替代全局 `trusted_mode`）。
2. **受信 Agent 边界**（能力白名单 + 项目范围 + 有效期，Agent 不能自续期）。
3. **模型路由与降级策略**（按能力声明、探活、降级后限权、恢复条件）。
4. **远程配置 / APK / 自迭代 / RCE** 这四类"对设备与自身的写操作"。
5. **习惯候选**（"建议·确认一次"、"仅今天应用"、不自动固化为长期规则）。

3. **导航形态**：现状控制台是 7 项侧栏（含「AI 对话」）；草图是 5 个平级 tab，
