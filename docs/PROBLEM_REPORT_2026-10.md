# Jarvis 项目问题报告与修补航向

> 版本：2026-10-06  
> 目的：把 Jarvis 从“可运行的个人 AI 原型”推进到“行为可预期、状态可追踪、风险可控的日常助手”。

## 1. 执行摘要

Jarvis 已经具备后端 API、事件运行时、任务/记忆/工具编排、设备 WebSocket、控制台和 Android/Wear OS 客户端等完整骨架。当前主要风险并非功能数量不足，而是核心闭环尚未足够可信：

> 输入被听到 → 意图被正确解释 → 动作被安全执行 → 用户知道结果 → 系统可恢复、可撤销、可追溯。

当前版本更适合实验性内测，不适合在没有人工观察的情况下托管重要提醒、设备控制或任意脚本执行。

## 2. 问题分级

### P0：必须优先修复

1. **额度只记录、不拦截**：ASR/LLM 调用前缺少原子预算检查，超限后仍可能继续产生费用；实时识别还存在重复提交累计音频的风险。
2. **确认语义不绑定原动作**：确认后的处理可能退化成“创建任务”，无法保证执行用户原本确认的工具动作；自然语言确认仅做关键词匹配，容易误判。
3. **设备成功状态不完整**：命令写入 WebSocket 不等于设备执行成功，`sent/delivered/seen/completed` 尚未完整区分。
4. **任意 Shell 执行面**：设备端通过 `sh -c` 执行脚本，服务端依赖黑名单审核，无法形成可靠的安全边界。

### P1：影响可靠性和日常体验

1. **时区不一致**：用户时区、安静时段、用量日切和任务解析混用 UTC/服务器本地时间。
2. **重启恢复不足**：部分运行时状态和队列留在内存，进程重启后可能丢事件、重复执行或漏提醒。
3. **采集失败静默丢失**：日历、通知、位置等上报缺少统一的本地队列、重试、去重和失败反馈。
4. **实时识别不是真正增量流式**：累计 PCM 反复调用文件式识别，延迟和费用可能随语音长度增长。
5. **活动流可追溯性不足**：缺少稳定 revision、增量游标、原始输入与工具证据的统一关联。
6. **记忆仍是关键词检索**：没有解决合并、冲突、遗忘、纠错、来源证据和语义召回。

### P2：产品和交互槽点

1. 控制台会在设备离线或感知未启用时仍显示“24 小时感知中”，制造虚假确定性。
2. 持续感知与手动录音的状态边界不清楚，用户难以判断当前是否正在录音、上传或识别。
3. 固定 VAD 阈值无法适配佩戴方式和环境噪声，可能误触发或漏听。
4. 提醒没有清晰区分发送、送达、已见、完成，重复提醒和错误完成的风险较高。
5. 历史活动缺少原始输入、判断理由、工具参数/结果和未执行原因，难以解释“系统刚才做了什么”。
6. 控制台聊天依赖 `sessionStorage`，关闭标签页后上下文消失。
7. 手表端职责集中在少数大类中，网络、音频、UI、任务和设备命令耦合，维护风险持续上升。

## 3. 修补航向

### 阶段 A：先恢复可信闭环

- 预算检查前置并保持原子性，超限时阻止新请求。
- 统一以用户时区处理安静时段、用量日切和自然语言时间。
- 为确认动作保存原始 action、能力、payload 哈希和过期时间。
- 明确设备命令状态机：`queued → sent → delivered → seen → completed/failed/expired`。
- 保留原始输入和规范化文本，失败必须可见、可重试、可去重。

### 阶段 B：收紧设备与权限

- 删除任意 Shell 作为远程能力入口，改用类型化、白名单化的设备能力。
- 设备命令增加 TTL、幂等键、ACK 等待、超时和失败原因。
- 设备 token 支持设备级轮换和撤销，避免“一个 token 控制所有设备”。

### 阶段 C：再做主动智能

- 持久化事件 revision 与增量同步游标。
- 增加离线队列、重启恢复和退避重试。
- 记忆增加来源、冲突、遗忘、纠错和用户可见删除。
- 控制台只显示真实设备/感知/ASR/TTS 状态，不再使用静态“全时在线”文案。

## 4. 本轮实际修补范围

本轮采用并行修补：

- `backend_trust`：预算、确认语义、时区与后端状态可靠性。
- `device_security`：设备命令、ACK、脚本执行面与 Android 端风险。
- `ux_stability`：控制台状态真实性、持久化体验、失败可见性和客户端交互。
- 主线程：问题报告、冲突整合、测试和最终验收。

## 5. 验收标准

1. `python -m pytest -q` 全部通过，且新增测试覆盖本轮根因修复。
2. `watch-client\\gradlew.bat assembleDebug` 通过；构建产物不作为源码提交。
3. 不新增 `#REF!`、`#DIV/0!`、未捕获异常或静默吞错路径。
4. 重要动作可回答：谁触发、何时触发、执行了什么、结果是什么、失败如何重试。
5. 报告中的 P0 问题有明确修复或明确列为剩余风险，不以“已发送”冒充“已完成”。

## 6. 当前定位

修补完成后，Jarvis 仍应被定位为**可观测的实验性个人助手**，而不是无需监督的全自动代理。只有在真实手表、弱网、后台重启、耗电、ASR/LLM 外部服务和设备 ACK 验证完成后，才适合扩大日常托管范围。
