# Jarvis 项目评估

版本：v0.1  
评估日期：2026-10-03  
评估范围：后端、事件运行时、AI 编排、`watch-client` Wear OS 客户端、中控台、文档与测试

## 1. 结论

### 2026-10-03 问答后的补充评估

原评级为静态代码阅读的主观分级，不是性能测试或生产认证。本轮仅改文档，未新增运行验证。
产品定位现已明确：个人生活/学习/工作的持续感知第二大脑，个人自用，不按比赛规划。
新的核心难点是门控质量、低成本长期感知、记忆证据链、可靠提醒及高权限行动，不再只是手表 UI。
单服务器和当前 SQLite 方向保留，多实例扩展不是本阶段优先级。
不要求开机自启、强制复活或离线智能；此前自动恢复与大离线队列建议以新基线为准。
用户接受全部设备资源投入，优化目的转为避免崩溃、发热、容量耗尽及无效 Token 消耗。
首要实验：日常声音分段/ASR/AI 态势判断与门控误介入率、5 秒首反馈、关联待办不重复创建、
断线后的提醒未送达状态、音频保留与增量记忆总结成本。
God Agent、海马体整理、统一活动流、多模型降级及受控远程自修改均为目标能力，不是现有完工项。
具体需求见 [确认基线](REQUIREMENTS_BASELINE.md)，设计见 [门控记忆架构](GATING_MEMORY_ARCHITECTURE.md)。
手表已确认有摄像头，由手表扫码配置；用户尚未收货，ADB 真机验证后续进行。
存储上限用户可配置，全量销毁延期；模型每日 5000 万 Token，ASR 独立限额 5 小时/日。代码调整属于需确认的自我迭代。

Jarvis 已经不是一个空白原型，而是具备可运行后端骨架的个人助理系统。当前最有价值的资产是统一事件模型、任务/记忆持久化、AI 决策、WebSocket 设备通道、确认动作和审计链。

项目当前不适合继续无边界地堆功能。下一阶段应从“功能原型”转向“产品化运行时”：

1. 先明确 Jarvis 的产品心智模型和核心用户路径。
2. 将事件、决策、任务、提醒、日志统一为一条可追踪的活动流。
3. 重构 `watch-client`，让手表成为稳定的感知与反馈终端。
4. 明确后台感知、通知、录音、位置、日历和 AI 主动行为的权限边界。
5. 用真实展讯 8521 手表验证功耗、保活、网络恢复和交互可读性。

| 领域 | 现状 | 评级 | 主要判断 |
| --- | --- | --- | --- |

| 事件运行时 | EventBus、去重、忽略规则已存在 | B- | 需要持久化运行状态和失败恢复 |
| AI 编排 | 分类、策略、工具循环和 Agent 已存在 | B- | 需要稳定输出协议和评估集 |
| 任务系统 | 状态、确认、重试、依赖、死信已存在 | B | 需要端到端时间线和幂等测试 |
| 记忆系统 | SQLite 记忆、项目和上下文已存在 | C+ | 需要生命周期、来源和修改模型 |
| 手表客户端 | 录音、WebSocket、前台服务、通知监听已有 | C | 原型可运行，架构和 UI 耦合严重 |
| UI 设计 | 示意图明确，现有实现偏离 | C | 需要严格按 360×480 重建 |
| 设置与配对 | 手动地址和 Token 可用 | C- | 应以扫码配置为主 |
| 隐私与权限 | 有基础权限申请和 Token 鉴权 | C | 需要完整的用户可见权限模型 |

总体评估：**后端核心 B-，手表产品化 C，整体处于“可运行技术原型”阶段。**

## 3. 已有资产

- `Event`、`EventBus`、标准化、去重和忽略规则。
- 任务创建、确认、取消、暂停、恢复、重试和死信字段。
- SQLite 中的事件、任务、记忆、项目、审计、设备和会话表。
- FastAPI HTTP/WebSocket 接口。
- AI 决策 action：回复、记忆、任务、确认、执行、忽略。
- Tool Registry、权限校验、超时和多轮工具循环。
- Android 录音分片、WebSocket 心跳、自动重连和本地命令回执。
- Android 通知、日历和位置事件入口。
- Edge TTS 分片推送协议。
- 基础中控台和后端自动化测试。

## 4. 关键问题

### 4.1 产品层

- Jarvis 的核心价值尚未被压缩成一条最重要的用户路径。
- “后台感知”“AI 介入”“提醒”“记忆”“任务”之间的关系需要统一解释。
- 主动行为的打扰等级和用户控制方式还没有成为产品规则。

### 4.2 数据层

- `events`、`audit_log`、`tasks`、`pending_actions` 可分别查询，但还不是统一活动流。
- Android 端目前无法可靠展示“已记录”“已拒绝”“已完成”等业务事实。
- 操作结果、撤销、修改和来源需要稳定 ID 以及关联关系。

### 4.3 Android 层

- `MainActivity` 同时承担页面、状态、网络、录音、TTS、历史和设置。
- UI 文字与数据状态混合，历史只能保存少量本地文本。
- 待确认动作通过自然语言“确认/暂不”间接处理，缺少明确 action ID。
- 前台服务以位置为主，录音、WebSocket、通知和生命周期没有统一运行时管理。
- 需要在 Android 8 / 展讯 8521 上实测后台限制、功耗和系统厂商行为。

### 4.4 可靠性层

- EventRuntime 的持久化恢复仍未完成。
- 多进程/多实例部署下的幂等和锁语义需要验证。
- 推送、TTS、录音上传和设备回执缺少完整链路测试。

### 4.5 安全与隐私

- Token 目前由设备配置保存，需补充存储保护、轮换和失效策略。
- 通知、位置、日历和语音均属于敏感数据，需要用户可见的采集范围和删除策略。
- AI 高权限执行必须继续经过 Policy、白名单、审计和可撤销设计。

## 5. 推荐技术方向

### Android

继续使用 Java + XML/View，不引入 Compose。原因：

- 目标设备 Android 8.0，硬件资源有限。
- 当前项目已经是 Java View 实现。
- 固定 360×480 页面适合轻量层级布局。
- 后台服务和网络代码不需要 Compose 才能完成。

建议拆分：

```text
MainActivity
  └── screen rendering and navigation only
RuntimeService
  └── lifecycle, foreground notification, collectors
SocketClient
  └── WebSocket, reconnect, heartbeat, inbound envelopes
AudioCapture
  └── permission, recording, chunking
ActivityStore
  └── local cache of server activity stream
JarvisRepository
  └── API and command operations
```

### 后端

继续使用现有 FastAPI + SQLite 起步，但先补齐：

- 统一 `activity` 读取模型。
- 事件、决策、任务、动作和审计之间的关联 ID。
- 可重复消费的设备消息协议。
- 持久化 AgentRun 和恢复策略。
- 真实设备测试夹具。

## 6. 风险清单

| 风险 | 影响 | 优先级 | 对策 |
| --- | --- | --- | --- |
| 手表后台被系统回收 | 感知和提醒失效 | P0 | 前台服务、保活实测、重连和离线队列 |
| 语音持续采集功耗过高 | 用户关闭功能 | P0 | 明确采集模式、采样率、空闲策略和电量策略 |
| AI 误触发高风险动作 | 信任和安全事故 | P0 | Policy、确认、白名单、审计、撤销 |
| 活动流无法解释 | UI 不可信 | P0 | 统一 Activity Contract |
| 通知/位置/日历过度采集 | 隐私风险 | P0 | 分项开关、来源显示、数据删除 |
| 设备与服务端协议漂移 | 线上故障 | P1 | 版本字段、契约测试和兼容策略 |
| 仅在模拟器验证 | 真实设备不可用 | P1 | 展讯 8521 真机矩阵 |
| 数据库单文件损坏或无备份 | 历史和任务丢失 | P1 | 备份、恢复演练和迁移脚本 |

## 7. 下一阶段完成定义

下一阶段不以“页面看起来完成”为完成标准，而以以下结果为准：

- 手表在 360×480 上完成主界面、活动流、确认卡片和日志详情。
- 一条用户输入可以从采集、服务端决策、活动流、确认/拒绝到反馈完整闭环。
- 断网、重连、重启和重复消息不会造成重复任务或错误状态。
- 后台感知、通知、位置、日历和录音均能单独关闭并显示真实状态。
- 每个 AI 行为都有来源、决策、结果、审计和撤销路径。
- 能在真实展讯 8521 手表上完成最小验收场景。
